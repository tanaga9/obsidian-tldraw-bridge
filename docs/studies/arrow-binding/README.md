# Arrow binding pattern study

Date: 2026-10-29. Environment: Obsidian tldraw plugin 1.32.0, using the
installed tldraw SDK 5.4.0 through Obsidian Tldraw Bridge. The SDK version is
recorded in the editable note metadata.

Status: experimentally informed recommendations for continued investigation.
The starting patterns and limitations have been reflected provisionally in the
[Arrow selection guidelines](../../arrow-selection-guidelines.md).
They are not adopted Skill guidance.

## Artifacts and method

- [Editable tldraw note](diagram.md)
- [WebP previews](previews/)
- [Structural and geometric verification](verification.json)
- [Construction script](generate.js) and [verification script](verify.js)

The note contains 53 arrows across eight pages, with 106 persisted bindings.
All arrows have two existing targets and belong to named frames. Each page was
exported through the actual tldraw renderer and visually inspected. Node moves
and dimension changes were performed through the Editor, rather than simulated
by drawing replacement lines. Relative path vertices were compared for the
controlled snap experiment.

This is an API-authored rendering and editing study. It does not test pointer
gestures, hover timing, or how the UI selects a binding during drawing. Some
deliberately inconsistent property combinations are diagnostic cases, not
recommended interaction states. Most nodes are unrotated rectangles. Findings
do not establish behavior for every geometry, rotation, crowded layout, SDK
version, or intervening obstacle.

## Main recommendation

Choose a connection intent, then apply a complete binding recipe including its
anchor. Avoid treating `snap`, `isPrecise`, and `isExact` as three independent
visual effects.

Use a center-directed, non-exact connection for an ordinary relationship between
whole nodes. Introduce explicit attachment positions when the position conveys
meaning or separates otherwise confusing connections. Use exact contact only
when reaching a particular point matters.

## Recommended recipes

The binding settings below apply per terminal. The two terminals need not use
the same recipe. Coordinates are relative to each bound node's bounding box.

| Intent | Arrow settings | Binding settings | Anchor |
| --- | --- | --- | --- |
| Ordinary relationship between whole nodes | `kind: arc`, `bend: 0` initially | `isPrecise: false`, `isExact: false`, `snap: none` | `(0.5, 0.5)` as a clear canonical value |
| Ordinary elbow connection with automatic attachment-side selection | `kind: elbow` | `isPrecise: false`, `isExact: false`, `snap: center` | `(0.5, 0.5)` |
| Deliberate side of entry or exit, including return paths | `kind: elbow` | `isPrecise: true`, `isExact: false`, `snap: edge-point` | Top `(0.5, 0)`, right `(1, 0.5)`, bottom `(0.5, 1)`, or left `(0, 0.5)` |
| Separate multiple connections along one side | `kind: elbow` | `isPrecise: true`, `isExact: false`, `snap: edge` | For example, left-side anchors `(0, 0.2)`, `(0, 0.5)`, `(0, 0.8)` |
| External self-loop | `kind: elbow` | Both ends `isPrecise: true`, `isExact: false`; use `edge-point` or `edge` | Two distinct boundary positions, for example right midpoint and top midpoint |
| Annotation pointing inside a node | `kind: arc`, usually straight | Target end `isPrecise: true`, `isExact: true`, `snap: none` | The intended internal point; leave the source non-exact if it represents a whole annotation node |
| Exact contact at an outline port | `arc` or `elbow` as appropriate | `isPrecise: true`, `isExact: true` at the end requiring contact | The actual boundary point; arc cases used `snap: none`, elbow cases used `snap: edge-point` |

The port row records the combinations actually tested. It is an API recipe, not
a claim about the snap value generated by an Alt-drag interaction.

## Findings and rationale

### 1. Center-directed arc is the best baseline for whole-node relationships

Page: [arc-center-vs-side](previews/arc-center-vs-side.webp).

For two wide rectangles placed diagonally, the center-directed straight line
looked like a connection between the nodes as wholes. Fixing both endpoints at
the midpoints of facing vertical sides produced a noticeably steeper line whose
extension missed the centers. This supports the visual-center criterion in the
established guidelines.

The distinction remained visible after moving the target above the source and
after enlarging it. Center direction adapted to the new centers; explicit
side-midpoint connections retained their specified attachment positions.

Recommendation: do not select side midpoints merely because they are regular
points. For ordinary relationships, prefer the line's natural relationship to
the nodes' visual centers.

### 2. Precise does not mean that the visible endpoint reaches the anchor

Page: [arc-precise-exact](previews/arc-precise-exact.webp).

With identical off-center anchor coordinates, all four boolean combinations
were rendered:

| `isPrecise` | `isExact` | Observed result |
| --- | --- | --- |
| `false` | `false` | Aimed at centers, stopped around the outlines |
| `true` | `false` | Aimed at specified points, but stopped around the outlines |
| `false` | `true` | Reached node centers, crossing the node interiors and labels |
| `true` | `true` | Reached the specified off-center internal points |

The third combination was accepted by the API but is a poor ordinary-node
default. The two flags describe different decisions: where to aim and whether
the visible terminal should actually reach the aim point.

### 3. Exact contact is not inherently internal contact

Page: [exact-at-outline](previews/exact-at-outline.webp).

At the same boundary-midpoint anchors, `isExact: false` left visible clearance
before the target outline, while `isExact: true` reached it. This occurred with
both straight arc and elbow arrows.

Recommendation: retain clearance for ordinary relationships when it helps the
arrowhead remain distinct. Choose exact contact when an actual point or port
must be touched. Avoid describing exact as simply “put the arrow inside”: the
anchor determines whether contact is inside or at the boundary.

### 4. Automatic elbow attachment adapts; explicit sides can create large detours

Pages: [elbow-patterns](previews/elbow-patterns.webp)
and [elbow-reversal](previews/elbow-reversal.webp).

With imprecise center bindings, moving the target from right to left or directly
below the source allowed the renderer to choose a corresponding entry/exit
side. The directly-below case became a simple vertical arrow.

With precise right-to-left boundary anchors, those same edits preserved the
specified sides, producing much longer routes around the nodes. This can be
desirable for an intentional return path, but is excessive for a generic
relationship. Precise interior anchors also influenced the chosen sides and
could create detours even with `snap: none`.

Recommendation: use automatic attachment for flexible whole-node elbow
connections. Specify sides to express intent, and review that intent again
after a major layout change. A valid binding does not guarantee a good route.

### 5. Multiple connections justify precise, separated edge anchors

Page: [recommended-use-cases](previews/recommended-use-cases.webp), section A.

Three input nodes connected to different positions along the left edge of a
service node remained individually traceable. Their target anchors were
`(0, 0.2)`, `(0, 0.5)`, and `(0, 0.8)`, with precise, non-exact edge bindings.

Recommendation: use this pattern when distinct lines would otherwise pile onto
one attachment point. The reason for explicit positions is connection
separation, not an assumption that every relationship needs a port.

Section B also shows a top-to-top elbow return path. In that case the departure
from center-directed connection is useful: the line visibly leaves the normal
flow and returns above the nodes.

### 6. Self-loops need distinct attachments and an external route

Page: [self-loop-patterns](previews/self-loop-patterns.webp).

The right-midpoint-to-top-midpoint elbow loop with `edge-point` routed clearly
outside the node. An `edge` variant with distinct boundary points also produced
a readable external loop.

The same midpoint anchors with `snap: none` produced a route within or along the
node. The imprecise center-to-center loop collapsed to zero length. Exact
internal anchors made an internal path overlapping the label. These are
unsuitable defaults for communicating a node's recurrence or retry.

A curved arc loop was possible, but the tested bend and anchors produced a
less controlled attachment direction. This single case does not rule out arc
loops; it supports elbow as the stronger starting pattern for an explicit
external return.

Recommendation: use two distinct boundary anchors and `edge-point` or `edge`
for both ends of an external elbow self-loop. Inspect the rendered loop and
its arrowhead; setting only `kind: elbow` is insufficient.

### 7. Snap alone is not a complete attachment instruction

Page: [snap-isolation](previews/snap-isolation.webp).

Four ordinary elbow connections used identical interior anchors, precise true,
and exact false. Only `snap` differed. All four produced identical relative
path vertices, confirmed in [verification.json](verification.json).

This deliberately diagnostic test shows that writing `snap: center` does not
by itself rewrite an arbitrary stored anchor to the center. Conversely,
`snap: none` does not mean “unbound” or “no routing constraints.” The self-loop
comparison also shows that snap is not universally irrelevant.

Recommendation: document snap together with anchor and boolean settings. Avoid
presenting it as an independent selector that automatically produces the named
attachment from any existing binding.

## Proposed decision order

1. Decide whether the relationship concerns whole nodes, particular sides,
   individual ports, or a point inside a node.
2. Choose `arc` or `elbow` according to the relationship and the desired visual
   reading, preserving the center-directed baseline for ordinary connections.
3. For whole nodes, start with imprecise and non-exact. For meaningful positions,
   use precise and choose the anchor deliberately.
4. Enable exact only where contact with the actual point is required.
5. For elbow, choose a snap value consistent with the complete recipe; give
   external self-loops explicit boundary attachments at both ends.
6. Review the rendered direction, center-of-gravity impression, clearance,
   arrowhead, label intersections, and detours after moving or resizing nodes.

## Limits and next questions

- Visual recommendations reflect this inspection and the user's stated
  center-of-gravity preference; they are not measured user-study results.
- Rotated nodes, nonrectangular shapes, open paths, and heavily crowded diagrams
  need separate checks before broadening the rules.
- Three independent lines entering one node do not establish good behavior for
  overlapping parallel arrows between the same pair of nodes.
- This study does not establish arbitrary obstacle avoidance by elbow routing.
- Pointer-generated settings should be investigated separately if the guideline
  will describe UI drawing gestures rather than SDK recipes.

This directory preserves the study separately from the guidelines so later
evaluation can revisit its evidence. No shared Skill rules or generated plugin
package were changed.


## Maintenance and reproduction

Keep this directory to 13 files: this explanation, the editable note, eight
WebP previews, one construction script, one verification script, and one final
verification record. Keep temporary exports, transport receipts, and intermediate
diagnostics outside tracked documentation.

`verification.json` preserves the original environment, saved drawing revision,
drawing hash, preview hashes and saved revisions, structural checks, and the
snap-isolation comparison. All file references are relative to this directory.
It is evidence of the original inspection, not a claim that future edits have
already been reviewed. When changing the diagram, update affected previews and
verification evidence together after inspecting the result.

### Recreate the cases

Use the current Obsidian Tldraw Bridge CLI and its `--help`. Resolve the intended
vault and run `doctor` before editing. Use a new, unused note path under the
vault's local workspace so reproduction does not overwrite this evidence.

1. Create a new tldraw note with `create` and an explicit unique request ID.
2. Run `generate.js` once through `script`, passing the newly created document's
   revision and a unique request ID. It performs all three construction phases
   synchronously, including the actual node moves and resizes.
3. Run `verify.js` against the resulting revision. Expect eight pages, 53 arrows,
   106 bindings, no structural issues, and matching relative paths for the four
   snap-isolation cases in the original environment.
4. Select each page through `apply` with `setCurrentPage`, then export through
   `preview`, using WebP, quality 0.9, and scale 0.6. Name the image after the
   page/frame. Keep intermediate outputs outside tracked documentation.
5. Inspect every image for connections, text, clipping, and detours, and confirm
   matching saved revisions. Record the actual installed plugin and SDK versions
   with new findings before revising any recommendation.

The construction script requires a fresh empty note with initial page ID
`page:page`; it rejects a populated note before mutation. Both scripts use the
SDK property schema tested here. Check that schema before running on a different
version. They contain no filesystem calls or asynchronous mutations. Some
combinations deliberately test inconsistent settings and are not recommended
recipes. On an uncertain outcome, inspect request status and the saved document
rather than blindly rerunning the generator.

Revisions, generated metadata, and raster bytes may differ on reproduction;
compare behavior and geometry rather than requiring identical file hashes.
The consolidated generator was checked against the original three scripts with
an in-memory Editor model: its Editor calls and resulting records matched,
including 53 arrows across eight pages, and its fresh-note guard rejected a
second run. This consolidation check does not replace live rendering review.
The saved diagram and inspected preview bytes were unchanged during consolidation.
