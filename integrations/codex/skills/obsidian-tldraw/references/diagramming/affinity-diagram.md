# Affinity diagrams

Use an affinity diagram to discover patterns together or explain patterns
already visible in source material. Choose the question the clusters should
answer. A retrospective might ask “What slowed down our release?” A portfolio
review might ask “What do these projects help people do?”

## Build the clusters

- Put one observation on each native tldraw sticky note (`note`). Start with
  the standard square and put the words in its own editable text field. Keep
  enough of the original wording and context for a reader to interpret the
  observation after moving it.
- Bring related notes together, then name the common thread in a separate
  editable heading. “Finding the build” tells readers why “The link took me to
  last week’s build” belongs there. Let the material determine how many
  clusters emerge. If participants are to do the sorting themselves, start
  with loose notes and let them supply the headings.
- When explaining a current situation to someone new to it, present an initial
  sort. Phrase each heading as something the reader can learn. For instance,
  “Reach files from the notebook” explains what two Jupyter extensions make
  possible. One note can name Box as the source and the other the user’s local
  disk. Check that the heading describes every note placed beneath it.
- Leave a note on its own or in a visibly separate unsorted area when its
  placement is open. An observation that fits two themes can stay there for
  discussion. Keep a single copy so later edits reach the original observation.
- Use proximity and clear gaps to show membership. Keep each note independently
  selectable and leave room to rearrange the board. A shared frame can hold the
  whole diagram. Cluster headings and sticky notes remain siblings within it.

## Cover a complete inventory

When asked for *all* items, establish the source list, its scope, and the date
for a changing collection. Use one note per item with a recognizable name and
a short, source-backed clue to its placement. Give each note a stable identity,
such as the repository URL in its native link field. Mark an attribute such as
fork status on the note when it matters across several clusters.

Count the saved sticky notes by item ID. Each source ID must appear exactly
once, and every saved note must carry an ID from the source list. If a card
needs a shorter display name, keep the full name and source in a linked inventory or in the
note’s [Markdown body](../operations.md#markdown-body-edits). When delivering
the board, explain one relationship the grouping reveals. Distinguish that
interpretation from a documented dependency or cause.

## Continue an existing sort

Read the current headings, note text, and positions before editing. Preserve
the participants’ wording and placements when adding material. Put a new note
under a heading when the requested change or source makes its placement clear.
Leave uncertain additions available to sort. Recluster existing notes when
the task calls for revisiting those relationships.

Inspect the saved board read-only at its intended viewing size. Check that
each heading reads with its notes and that undecided notes look separate from
established clusters.

To test editing, make a disposable copy of the board. In that copy, move a
sticky note between clusters, rename a heading, duplicate a sticky note, and
edit the duplicate’s text. Reopen the disposable board and verify the move,
the new heading, and the distinct text on the two sticky notes.
